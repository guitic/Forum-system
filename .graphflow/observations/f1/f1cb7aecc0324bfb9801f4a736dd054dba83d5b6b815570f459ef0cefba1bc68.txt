1: # 在线论坛系统 V3.0 - 帖子回复与层级回复（楼中楼）功能
2: 
3: ## 1. 功能概述
4: 
5: 在 V2.0（用户中心）基础上新增**层级回复**能力，让讨论从"平铺列表"升级为"话题树"：
6: 
7: | 功能 | 说明 |
8: |------|------|
9: | **进入帖子并回复** | 点击帖子卡片进入详情页，发表评论参与讨论 |
10: | **回复某条回复** | 在任意回复下点击「回复」，针对该条回复继续讨论 |
11: | **层级感** | 子回复缩进展示，最多 3 层，带左侧引导线 |
12: | **凸显楼主** | 帖子作者（OP）在所有场景中佩戴「楼主」徽标，卡片有主色左边框 |
13: | **凸显管理员** | 管理员回复佩戴 ADMIN 徽标，头像使用琥珀色 |
14: | **删除回复** | 回复作者或管理员可删除自己的回复，级联删除其下所有子回复 |
15: | **引用提示** | 被回复人显示在子回复顶部：`回复 @用户名` |
16: 
17: ## 2. 方案选型
18: 
19: ### 2.1 候选方案对比
20: 
21: | 方案 | 结构 | 优点 | 缺点 | 结论 |
22: |------|------|------|------|------|
23: | **A. 无限嵌套** | `parent_id` 自引用，深度不限 | 最灵活 | 深层内容缩进过深不可读；递归查询与维护成本高 | ❌ |
24: | **B. 固定层级 + 溢出拉平** | `parent_id` + 深度上限，超出后挂载到上一级祖先 | 结构可控、UI 可读、查询简单，符合主流论坛（贴吧/知乎/掘金） | 需约定层级上限 | ✅ **选用** |
25: | **C. @提及 + 引用** | 无树结构，纯文本 @ | 实现最简单 | 无层级感，不满足需求 | ❌ |
26: 
27: ### 2.2 选用方案 B 的规则
28: 
29: - **层级上限**：`MAX_REPLY_DEPTH = 2`（即 3 层：一级回复 → 二级 → 三级）
30: - **深度定义**：一级回复 `depth = 0`，其子回复 `depth = 1`，以此类推
31: - **溢出策略（展示期拉平）**：数据库保留**真实父子关系**，当某条回复 `depth > 2` 时，前端展示阶段将其上提到 `depth = 1` 的祖先下作为同级，并保留 `@被回复人` 引用。这样既不丢失真实关系，又保证界面最多 3 层缩进。
32: 
33: ## 3. 数据库变更
34: 
35: `replies` 表新增 2 个字段：
36: 
37: | 字段 | 类型 | 约束 | 说明 |
38: |------|------|------|------|
39: | `parent_id` | INT | 可空，外键 → `replies.id` | 直接父回复 id；为 NULL 表示一级回复（话题根） |
40: | `root_id` | INT | 可空，外键 → `replies.id` | 所属话题根回复 id；一级回复在库中存 NULL，**API 读取时统一解析为其自身 id** |
41: 
42: 新增索引：`idx_reply_parent(parent_id)`、`idx_reply_root(root_id)`
43: 
44: > **字段设计意图**
45: > - `parent_id`：表达直接父子关系，用于构建真实树
46: > - `root_id`：冗余存储话题根 id，便于按话题聚合查询与前端锚点跳转，避免递归查询。API 层对所有回复都返回非空值（一级回复返回自身 id），前端可直接 `group by root_id`
47: > - `depth`：**不落库**，由后端在读取时按 `parent_id` 链实时计算，避免脏数据
48: 
49: ### 3.1 存量数据库兼容
50: 
51: - **MySQL / MariaDB 生产环境**：执行 `database/migration_v3.sql`
52: - **本地 SQLite 开发库**：运行 `python init_db.py` 时自动检测并补列 + 补索引（幂等）

117: ### 4.2 发布回复（增强）
118: 
119: ```
120: POST /api/posts/{id}/replies
121: Header: Authorization: Bearer <token>
122: 
123: Body:
124: {
125:   "content": "回复内容（必填）",
126:   "parent_id": 10        // 可选；省略或 null = 一级回复
127: }
128: 
129: 校验规则：
130: 1. content 不能为空白
131: 2. parent_id 非空时，父回复必须存在
132: 3. 父回复必须属于同一帖子（post_id 一致）
133: 4. 不允许回复已删除的回复
134: 
135: 深度处理：
136: - 新回复真实深度 = 父回复深度 + 1（parent_id 保留真实目标）
137: - root_id（库列）：父回复是子回复时取父回复的 root_id；父回复是一级回复时置 NULL（读取时由 API 解析为父回复 id）
138: - 若超过 3 层，由前端展示阶段拉平（数据库不修改）
139: 
140: 响应（201）：返回新回复对象，字段同 4.1 中的节点结构
141: ```
142: 
143: ### 4.3 删除回复（新增）
144: 
145: ```
146: DELETE /api/replies/{reply_id}
147: Header: Authorization: Bearer <token>
148: 
149: 权限：仅回复作者本人或管理员（role='admin'）
150: 
151: 行为：级联删除该回复及其所有子孙回复（事务保证）
152: 
153: 响应（200）：
154: {
155:   "message": "删除成功",
156:   "deleted_count": 3        // 本次实际删除的回复条数（含自身）
157: }
158: 
159: 错误：
160: - 404 回复不存在
161: - 403 无权删除该回复
162: ```

164: ## 5. 前端页面设计
165: 
166: ### 5.1 帖子详情区（楼主凸显）
167: 
168: - 标题下方 meta 栏：头像 + 昵称 + **「楼主」徽标** + 时间 + 回复数
169: - 楼主头像使用主色渐变，管理员使用琥珀色渐变
170: - 若当前登录用户是楼主，右上角显示「删除」按钮
171: 
172: ### 5.2 回复树渲染
173: 
174: - 顶部显示 `回复 <count>` 统计
175: - 一级回复平铺；子回复缩进并带左侧引导线（2px 边框）
176: - 每层缩进宽度 52px（一级回复宽度），缩进量逐级递增
177: - 每条回复底部操作栏：`回复` / `删除`（仅本人或管理员）
178: 
179: ### 5.3 内联回复表单
180: 
181: 点击某条回复的「回复」按钮：
182: 
183: 1. 关闭其他已打开的内联表单（同一时间只存在一个）
184: 2. 在该回复所在子树**末尾**插入内联表单
185: 3. 表单顶部显示引用条：`回复 @目标用户名`（带关闭按钮）
186: 4. 自动聚焦并预填 `@目标用户名 `（含空格）
187: 5. 提交成功后关闭表单并刷新回复树
188: 6. 支持 `Ctrl/Cmd + Enter` 快捷提交
189: 
190: ### 5.4 角色徽标体系
191: 
192: | 身份 | 徽标 | 位置 | 颜色 |
193: |------|------|------|------|
194: | 楼主（帖子作者） | `楼主` | 名称右侧 | 绿色 `#d1fae5 / #047857` |
195: | 管理员 | `ADMIN` | 名称右侧 | 琥珀色 `#fef3c7 / #92400e`（沿用） |
196: | 回复作者 | （无徽标） | — | — |
197: 
198: > 一名用户可同时是楼主和回复者：此时其回复同时佩戴 `楼主` 徽标。管理员若是楼主则两个徽标都显示。
199: 
200: ### 5.5 楼层序号
201: 
202: 一级回复左侧显示序号 `#1`、`#2`…，帮助读者定位话题根；二级/三级回复不显示序号，通过缩进体现层级。

204: ## 6. 安全要求
205: 
206: | 项目 | 要求 |
207: |------|------|
208: | **鉴权** | 发布/删除回复均需 Bearer Token；帖子详情与回复列表对游客开放 |
209: | **权限** | 删除回复仅作者或管理员；删除帖子沿用现有逻辑 |
210: | **XSS** | 回复内容沿用 `marked.js` + 白名单 `API.sanitize` 清洗 |
211: | **引用文本** | `@用户名` 引用以前端文本节点渲染，不做 HTML 解析 |
212: | **深度校验** | 服务端校验 parent_id 归属同一帖子，防止跨帖挂接 |
213: | **级联删除** | 事务内批量删除，避免产生孤立引用 |
214: 
215: ## 7. 层级拉平算法（后端）
216: 
217: ```
218: 输入：replies（按 created_at 升序）
219: 输出：reply_tree（展示用树，最多 3 层）
220: 
221: 1. 建立 id → node 索引
222: 2. 对每条回复计算真实 depth：沿 parent_id 链向上回溯到一级回复
223: 3. 计算 root_id：一级回复解析为其自身 id，其余继承其一级祖先 id
224: 4. 构建展示树：
225:    - depth <= MAX_REPLY_DEPTH 的节点挂到真实父节点下
226:    - depth > MAX_REPLY_DEPTH 的节点上提到「depth == 1 的祖先」下作为同级
227: 5. 统计每个节点的 reply_count（直接子回复数）
228: ```

232: | 项目 | 影响 |
233: |------|------|
234: | `GET /api/posts/{id}` | 新增 `reply_count` / `reply_tree` 字段；保留 `replies` 字段（向后兼容） |

237: | 前端 `post.js` | 回复渲染逻辑重写为递归；一级回复交互保持不变 |
238: | 本地 SQLite | `init_db.py` 自动补列，无需手工干预 |
239: | 生产 MySQL | 需执行 `database/migration_v3.sql`（`ADD COLUMN IF NOT EXISTS` 幂等） |
